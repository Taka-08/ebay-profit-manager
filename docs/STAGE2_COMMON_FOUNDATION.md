# 第2段階 共通基盤

## 目的

既存の利益計算、送料計算、出品管理、分析を変更せず、将来の商品マスター、在庫、承認、eBay API、注文、発送、AI実行履歴を同じ商品から追跡できる最小基盤を追加する。

## 追加スキーマ

- `schema_migrations`: 適用済みマイグレーションを一意なIDで記録する。
- `products`: 新規登録商品の親レコード。`product_id` は `prd_` 接頭辞付きUUID4。
- `outbox_events`: 外部API処理をDB更新と同じトランザクションへ記録する将来用キュー。
- `audit_logs`: 人間、AI、システムによる変更理由と前後値を記録する。
- `listings.product_id`: 既存表へ追加するnullableな論理リンク。既存行は自動更新しない。

マイグレーションは追加のみで、既存テーブルや列の削除、型変更、既存行のバックフィルを行わない。SQLiteとTurso/libSQLで共通のSQL範囲を使う。

## 新規登録のトランザクション

`ListingRegistrationService` は、1つのトランザクション内で次を行う。

1. `products` に商品を作成する。
2. 同じ `product_id` を付けて既存 `listings` に登録する。
3. `audit_logs` に `listing.registered` を記録する。
4. 将来必要な場合だけ、同じトランザクションでOutboxイベントを追加できる。

途中で失敗した場合は全処理をロールバックする。従来の `shipping_breakdown_json` を含む登録辞書はそのまま `ListingRepository` へ渡し、送料スナップショットの構造や計算結果を変更しない。

現行UIには既存商品を選ぶ商品マスター操作がないため、利益計算からの明示的な新規登録1回につき新しい `product_id` を発行する。同名・同一SKUを推測で統合しない。既存出品の複製処理が `product_id` を持つ行を複製する場合は、同じ商品の複数出品としてリンクを維持する。

## ID方針

システム内部IDはエンティティを示す短い接頭辞とUUID4を組み合わせる。分散環境や非同期処理で中央採番を必要とせず、衝突可能性を十分に低くする。

例: `prd_<uuid>`、`evt_<uuid>`、`aud_<uuid>`。将来の在庫、利益計算、送料見積、下書き、承認、販売出品、注文、発送、タスク、AI実行にも同じ生成器を使える。

eBay Item IDなどの `external_listing_id` は外部サービスが発行する識別子なので、内部ID生成器では生成せず、将来 `marketplace_listing_id` と分離して保存する。

## Outboxと冪等性

`outbox_events.idempotency_key` は一意制約を持つ。同じキーを再登録した場合は最初のイベントを返し、重複イベントを作らない。WorkerとeBay API呼び出しはこの段階では実装しない。

## 金額方針

既存 `listings` の `REAL` 列は後方互換のため変更しない。将来追加する正規化テーブルでは次を原則とする。

- JPY: 1円を最小単位とする整数。
- 外貨: ISO 4217のminor unit整数、または桁数を明示したDecimal相当。
- 為替: 浮動小数の暗黙丸めを避け、文字列表現またはscale付き整数で保存する。
- 計算結果: 通貨、丸め方式、数式バージョン、計算日時をスナップショットとして保持する。

全面移行は別段階とし、既存金額や過去の利益・送料を現在の式で再計算しない。

## 今回の非対象

AI生成、承認UI、eBay API、仕入先監視、注文・発送同期、Worker、大規模UI統合は未実装である。
